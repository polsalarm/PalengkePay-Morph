The Answer

PalengkePay, in 6 questions

Who

Palengke vendors & their customers — plus market admins who onboard them. Mostly unbanked, cash-only.

What

QR micropayments + utang (buy-now-pay-later) that settle on Stellar, building each vendor a verifiable financial identity.

When

Real-time — payments confirm in seconds. Utang runs on weekly installment schedules with a grace period.

Where

In the palengke, on a budget phone — an installable PWA. Money lives on-chain; profiles off-chain.

Why

Fintech treats vendors as invisible: no merchant account, card fees kill margins. They deserve a zero-barrier door in.

How

3 Soroban contracts (Rust) + a React PWA, wallets via Stellar Wallets Kit, gasless through fee-bump. Deployed on Vercel.

The On-Chain Layer

Smart contracts on Soroban

Soroban is Stellar's smart-contract platform. Contracts are Rust compiled to WASM. They hold the money logic — anything involving value lives here, where it's verifiable and can't be quietly changed.

Contract 1

VendorRegistry

Identity. Maps a wallet → vendor record, applications, stats & ratings.

Contract 2

PalengkePayment

Settlement. Executes the XLM transfer and records every payment.

Contract 3

UTangEscrow

Credit. Holds buy-now-pay-later installments, grace & defaults.

Each contract: initialize() sets admin + token · state in typed storage · require_auth() guards who can call what · upgrade() swaps WASM without losing data.

The Handshake

How contracts & wallets work together

The contract never trusts the frontend. It trusts a signature. The wallet proves identity with require_auth(); the user's key authorizes the exact call.

Multi-wallet

Stellar Wallets Kit abstracts Freighter, Lobstr, xBull, Albedo & WalletConnect behind one API.

Gasless for vendors

A sponsor wallet fee-bumps the transaction — vendors pay nothing to receive money.

The Frontend

It depends… but use TypeScript.

Your frontend framework is a preference — React, Vue, Svelte all work. But for Stellar & Soroban specifically, the language matters — and TypeScript is the clear pick.

React · Vite · Tailwind · PWA
The big reason

The SDK is TypeScript-native

@stellar/stellar-sdk ships its own types — XDR, transactions, RPC responses all typed end-to-end. And stellar contract bindings typescript generates a fully-typed client straight from your deployed contract, so a wrong argument fails at compile time — before it ever costs real XLM.

Wiring It Up

Connecting the frontend to deployed contracts

1
Save each contract ID in an env var. Never type it into your code.
2
Run the CLI once per deploy. It turns your contract into a typed client you can import.
3
Create the client with three things: the contract ID, the RPC URL, and the network.
4
Call a function → the wallet signs it → send it → read back the result.

⚠ Redeploy = NEW contract ID. Update env + Vercel every time.

// 1 · typed client from generated bindings import { Client } from 'palengke_payment'; const payment = new Client({ contractId: import.meta.env.VITE_PAY_ID, rpcUrl: import.meta.env.VITE_RPC_URL, networkPassphrase: WalletNetwork.TESTNET, }); // 2 · build → wallet signs → submit const tx = await payment.pay({ customer, vendor, amount, memo, }); await tx.signAndSend({ signTransaction }); // → reads back the typed payment_id ✓
